NULL is the same binary with ARCHON_NARROW=0 (loader declines to pack), so the
`.text`, the dispatch and the tree are identical and the ONLY difference is
whether 10,409,593 of the frame's 19,616,896 folded threat rows are stored in
960 bytes or 1280.

Demand bytes the arm removes: 10,409,593 rows x 320 B = 3.331 GB, plus the
narrow share of thr_refresh's 407,362 rows ~= 0.069 GB, = 3.400 GB of the
45.94 GB the frame folds (35,888,218 rows x 1280 B) = 7.40 %.

Every memory counter moves the WRONG way. See §2.3 of the study doc: the row
keeps its 1280-byte slot, so a narrow row leaves a dead 320-byte tail, and the
L2 streaming prefetcher fetches it anyway (+18.90 % prefetch hits) at the cost
of evicting rows that were going to be used (+13.23 % L2 misses).
