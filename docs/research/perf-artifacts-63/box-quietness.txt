### NOTE ON LOAD AVERAGE AS A QUIETNESS METRIC (perf study 63)
A wall-clock panel spawns 3 processes per round -- 1200 in the 400-round panel --
so its own spawn rate inflates `load average` while it runs (3.75 / 5.11 after the
5-minute startup panel). The load average during a panel is therefore NOT a
quietness metric; the PROCESS CENSUS is.

### CORRECTION -- THE FIRST PANEL WAS NOT QUIET, AND MY CENSUS COULD NOT SEE IT
An earlier version of this note claimed "no other study, no match, no build ran at
any point during any panel in this study". That is FALSE for the first (400-round,
18:59-20:11) panel, and the receipt is in git: a concurrent session on this box ran
a 400-game fixed-node match (`d990a1bd`, committed 19:18:30) and a wall-clock smoke
test of its own against the same PGO pair (`4fecb7c1`, committed 20:03:14, whose
message says it was run "while perf study 63 was running its own panel"). Both fall
inside that window.

A before/after process census CANNOT see a job that starts and ends between the two
checks. That is the defect in the discipline, not in the box: the check must run
DURING the panel, which is what `wallclock_panel.py`'s new busy-fraction sampling
(`4fecb7c1`) exists for.

It does not change the first panel's verdict -- it was already void -- and it does
not explain that panel's null BIAS, which cancels within a round for any load that
inflates all three binaries. It does mean the sd improvement 3.58% -> 1.44% is
CONFOUNDED between the pinning fix and a quieter box; only the null median
(+0.646% -> -0.051%) is cleanly attributable to the tmpfs fix.

The second (210-round, 20:16-20:52) panel's before and after censuses are identical
-- the GPU trainer and a browser, nothing else -- the concurrent session's commits
